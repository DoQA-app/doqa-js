# Адаптер DoQA для Jest

[![CI](https://github.com/doqa-app/doqa-js/actions/workflows/ci.yml/badge.svg)](https://github.com/doqa-app/doqa-js/actions/workflows/ci.yml)
[![npm](https://img.shields.io/npm/v/@doqa-tms/jest?label=@doqa-tms%2Fjest)](https://www.npmjs.com/package/@doqa-tms/jest)
[![License](https://img.shields.io/badge/license-Apache--2.0-blue)](LICENSE)

Адаптер `@doqa-tms/jest` передаёт результаты тестов Jest в [DoQA](https://doqa.app). Он отправляет
их через API DoQA или сохраняет в файлы Allure-совместимого формата, которые можно загрузить в DoQA
позже. Вместе с исходом теста адаптер передаёт шаги, фикстуры, вложения, параметры и метаданные.

Адаптер работает с Jest 29.7 и 30 и стандартным раннером jest-circus. Существующие тесты менять
не нужно: адаптер учитывает тесты, объявленные через `test` и `it`. Объект `doqa` нужен только для
дополнительных данных: шагов, вложений, идентификаторов автотестов и ссылок.

Ошибки отправки не меняют результат прогона Jest. Если DoQA недоступен или отклоняет запрос,
адаптер выводит предупреждение в stderr и записывает в файлы результаты, которые не удалось
отправить.

## Требования

- Node.js 22 или 24. На этих версиях адаптер проверяется в CI; в `package.json` указано
  `node >=22`.
- Jest 29.7 или 30. Пакеты `jest`, `jest-environment-node` и `@jest/test-sequencer` указаны
  как peer-зависимости адаптера.
- `jest-environment-jsdom` той же версии, если тесты используют среду `jsdom`.

## Установка

```sh
npm install --save-dev @doqa-tms/jest
```

Подключите адаптер в конфигурации Jest:

```js
// jest.config.cjs
const { withDoqa } = require('@doqa-tms/jest');
module.exports = withDoqa({ testEnvironment: 'node' });   // второй аргумент - настройки адаптера, необязателен
```

`withDoqa` возвращает переданную конфигурацию Jest, в которую добавлены reporter адаптера и
обёртки над средами `node` и `jsdom`. Вторым аргументом передаются настройки адаптера.

## Быстрый старт

### Сохранение результатов в файлы

Если подключение к DoQA не настроено, адаптер работает в файловом режиме. Запустите тесты
(`npx jest`). После прогона в каталоге `results/` рабочей директории появятся файлы
`<uuid>-result.json` в Allure-совместимом формате. Тестовому процессу в этом режиме не нужны ни
доступ к DoQA, ни токен.

Если настройки подключения не заданы, адаптер выводит предупреждение `DoQA: no reporting
configuration found (missing …)`: результаты не отправлены в DoQA. Если файловый режим выбран
намеренно, задайте `reporting=files`, и предупреждения не будет.

Загрузить файлы в DoQA можно командой `doqactl upload` или отдельным шагом CI. Пример для GitLab CI
приведён в [README адаптера](doqa-jest/README.md).

### Отправка результатов в DoQA

Для отправки через API нужны три настройки: адрес DoQA, токен и id пространства. Задайте их в файле
`doqa.properties` в каталоге, из которого запускается Jest, или в переменных окружения:

```properties
# doqa.properties (или DOQA_URL / DOQA_TOKEN / DOQA_SPACE_ID в CI)
url=https://demo.doqa.app
token=<project token>
spaceId=42
```

Когда заданы все три значения, адаптер при старте Jest создаёт прогон в DoQA. После завершения всех
тестов он отправляет в этот прогон результаты пакетами по 100 штук (настройка `batchSize`). Чтобы
результаты отправлялись после завершения каждого тестового файла, включите `importRealtime`.

Если настройки подключения лежат в `doqa.properties`, в DoQA отправляется каждый запуск тестов,
включая локальные. Поэтому их обычно задают только в CI через переменные окружения `DOQA_URL`,
`DOQA_TOKEN` и `DOQA_SPACE_ID`. Остальные настройки, режимы прогона и устранение неполадок описаны в
[README адаптера](doqa-jest/README.md).

## Что передаёт адаптер

Для каждого теста адаптер передаёт исход, время выполнения, сообщение об ошибке и stack trace.
Исход `failed` означает, что не выполнилась проверка (`expect`, `node:assert`, chai). Исход
`broken` означает другую ошибку: исключение, таймаут или падение хука. Пропущенные тесты
(`test.skip`, `test.todo`) передаются с исходом `skipped`.

Хуки `beforeEach` и `afterEach` попадают в отчёт как шаги setup и teardown теста. Хуки
`beforeAll` и `afterAll` попадают в setup и teardown каждого теста своего `describe`-блока. Внутри
теста и хуков можно вызывать методы объекта `doqa`: `doqa.step` добавляет вложенные шаги,
`doqa.attach` и `doqa.attachFile` добавляют вложения, `doqa.parameter` добавляет параметр,
`doqa.metadata` задаёт идентификатор, название, описание, ссылки, метки, теги и привязку к ручным
кейсам.

### Идентификатор автотеста

DoQA связывает результат с автотестом по идентификатору. Адаптер берёт его из `id` в метаданных
теста или из названия теста в форме `[DOQA-123]` или `@DOQA:123`. Если идентификатора нет, адаптер
вычисляет хэш от имени проекта Jest, пути к тестовому файлу, названий `describe`-блоков и названия
теста. У такого теста переименование, перенос в другой `describe`-блок или в другой файл меняют
идентификатор, и DoQA создаёт новый автотест без прежней истории. Чтобы история сохранялась,
задайте тесту `id`.

### Запуск выбранных тестов

Когда DoQA запускает выбранные автотесты в CI, он передаёт в пайплайн переменные `DOQA_TEST_RUN_ID`
и `DOQA_ADAPTER_MODE=0`. В этом режиме адаптер получает из DoQA список автотестов прогона и
выполняет только тесты из этого списка. Остальные тесты Jest показывает как `skipped`, в DoQA они
не отправляются.

С настройкой `executionOrder: 'plan'` адаптер выполняет тестовые файлы и тесты в порядке плана
DoQA. Если применить этот порядок нельзя, адаптер выводит предупреждение и оставляет порядок Jest.

### Параллельный запуск

Прогон в DoQA создаёт reporter в главном процессе Jest. Workers к DoQA не обращаются: они
записывают результаты в каталог `.doqa/` рабочей директории, а reporter читает их оттуда и
отправляет. Отдельная настройка для параллельного запуска не нужна.

### Ошибки при отправке

Если адаптеру не удалось создать прогон или получить список выбранных тестов, он записывает все
результаты в `results/`. Если DoQA отклонил пакет результатов во время прогона, в файлы
записывается только этот пакет, следующие пакеты адаптер продолжает отправлять. В обоих случаях
адаптер выводит предупреждение с причиной и записывает в `results/` файл
`doqa-reporting.properties`. По этому файлу шаг CI может определить, какие результаты нужно
загрузить в DoQA отдельно.

## Архитектура

Код разделён на три модуля и публикуется одним npm-пакетом `@doqa-tms/jest` из корня репозитория.
Отдельных пакетов `doqa-client` и `doqa-js-commons` в npm нет: их код доступен по подпутям пакета.

| Модуль | Импорт | Назначение |
|---|---|---|
| [`doqa-jest`](doqa-jest/README.md) | `@doqa-tms/jest` (= `@doqa-tms/jest/jest`) | адаптер Jest: `withDoqa`, объект `doqa`, reporter, среды и sequencer |
| [`doqa-js-commons`](doqa-js-commons/README.md) | `@doqa-tms/jest/commons` | часть, не зависящая от Jest: настройки, шаги и вложения, отправка результатов, запись файлов |
| [`doqa-client`](doqa-client/README.md) | `@doqa-tms/jest/client` | HTTP-клиент DoQA Autotest API |

Отдельными подпутями доступны также `@doqa-tms/jest/reporter`, `@doqa-tms/jest/environment-node`,
`@doqa-tms/jest/environment-jsdom`, `@doqa-tms/jest/sequencer`, `@doqa-tms/jest/commons/session` и
`@doqa-tms/jest/commons/coordinator`.

```
ваши тесты ──► doqa-jest (адаптер) ──► doqa-js-commons (ядро) ──► doqa-client (HTTP) ──► DoQA
```

Пакет устанавливает одну зависимость, `undici`; её использует `doqa-client`. Jest и его среды
указаны как peer-зависимости.

Модули `doqa-js-commons` и `doqa-client` не зависят от Jest. В [README `doqa-js-commons`](doqa-js-commons/README.md)
описано, как построить на них адаптер для другого тестового фреймворка. Если адаптера для вашего
фреймворка нет, напишите в поддержку support@doqa.app.

## Разработка

Для сборки нужен Node.js 22 или 24:

```sh
npm ci
npm run lint
npm test
npm run pack
npm run test:packages
```

- `npm run lint` проверяет типы TypeScript.
- `npm test` собирает пакет и запускает тесты клиента, общей части и адаптера. Часть тестов адаптера
  запускает Jest в дочерних процессах.
- `npm run pack` собирает архив пакета в `release-dist/`.
- `npm run test:packages` устанавливает этот архив во временный проект и проверяет импорт.

Релиз выпускается тегом `v<версия>`. Workflow `release.yml` публикует пакет `@doqa-tms/jest` в npm и
создаёт GitHub Release, в котором заметки к релизу сгруппированы по меткам `type:` у pull request.
